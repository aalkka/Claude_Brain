# 배경 태스크가 15분 유휴에 무성 종료된다

## 증상

`run_in_background` 로 띄운 장시간 프로세스가 **아무 오류 없이** 사라진다.
그런데 **배경 태스크 목록은 계속 `running` 으로 보인다.** 그래서 *"1시간 돌린다"*
고 해 놓고 **15분에 끝나는데 우리는 그것을 모른다.**

⚠ **이 결함의 핵심은 죽는 것이 아니라 죽은 것을 못 아는 것이다.** 프로세스가
곧바로 죽으면 알아채지만, 상태가 `running` 으로 남으면 **결과가 잘린 채로
분석까지 흘러간다.**

## 조건

- **Claude Desktop for Windows** (임베드 CLI). 표준 CLI(`~/.local/bin/claude`)나
  OS 수준 스케줄링으로 띄운 것은 **살아남는다.**
- 세션 **탭이 숨겨진 상태**(`timeoutOnHidden: true` · 탭이 보이면 타이머가 안 돈다)
- **~15분 유휴**(`idleTimeoutMs: 900000`)

## 근본 원인

`WarmLifecycle` 의 유휴 세션 재활용이다 —

    onDisconnect -> pauseSession -> teardownSession(id, "pause") -> teardownQuery -> query.close()

윈도우에서 `query.close()` 가 `taskkill /pid <pid> /T /F` 를 부른다. **`/T` 가
프로세스 트리 전체**를 죽이므로 CLI 의 `run_in_background` 자식이 함께 죽는다.
그리고 `teardownQuery` 가 비동기 핸들만 null 로 만들고 **태스크 상태를 조정하지
않아** 목록이 `running` 에 머문다.

출처 = [anthropics/claude-code#68625](https://github.com/anthropics/claude-code/issues/68625)
(이슈 본문·디컴파일 코드 인용 · 2026-09-04 열람). **설계된 동작이지 일시적 크래시가
아니다.** macOS 도 `process.kill(-pid, "SIGTERM")` 경로로 영향받을 수 있다.

⚠ **우리 환경에서 15분을 직접 기다려 재현하지는 않았다.** 근거는 이슈 본문이다.
다만 아래 해결책은 어느 쪽이 참이든 안전하므로 재현을 기다릴 이유가 없었다.

## 해결 — 런처를 한 단계 거쳐 분리 기동한다

`taskkill /T` 는 **스냅샷 시점의 부모-자식 관계**를 따라간다. 중간 런처가 손자를
띄우고 **즉시 죽으면** 추적이 끊긴다.

    부모 -> 런처(즉시 종료) -> 실제 작업 프로세스
    런처는 DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW 로 띄운다

**실측**(`measure/probe_detach.py` · 측정 도구 저장소 · 대조군 포함) —

    직접 기동  taskkill /PID <부모> /T /F 뒤  +0줄   -> 죽음  (대조군이 옳게 죽어 탐침도 검증됨)
    분리 기동                                +11줄  -> **살아남음**

구현 = 제작자 볼트의 화면 관측 도구 기동 명령. 같은 수법을 다른 장시간 작업에도 쓸 수 있다.

## ⚠ 해결이 새 위험을 만든다 — 정지 경로를 반드시 함께 만들 것

분리한 프로세스는 **Claude Code 가 죽어도 안 멈춘다.** 그래서 정지가 여럿이어야
한다(kill switch 원칙: *정지가 앱의 UI 에 의존하면 안 된다*) —

1. **시간 상한**(`--seconds`) — 유일한 **자동** 제동
2. **정지 파일**(`STOP`) — CLI·GUI 어느 쪽에서 만들어도 된다
3. **인터럽트 안전망** — 그래도 죽으면 잔여를 회수하고 닫는다

⛔ **`taskkill`·Ctrl+C 를 정지 경로로 쓰지 마라.** 눈에서 실측했다 —
프레임 루프 밖에 마무리 코드가 있어서 `observations.md` 가 **0바이트**로 남았다
(관측 결과를 통째로 잃는다).

## 재발 방지

- **장시간(>15분) 작업은 `run_in_background` 로 띄우지 않는다.** 분리 기동하거나
  사용자가 직접 터미널에서 돌린다.
- **배경 태스크의 `running` 을 살아 있음의 증거로 쓰지 않는다.** 프로세스가 실제로
  일하고 있다는 증거는 **산출 파일이 자라는 것**이다(눈은 `hud.json` 에 경과를 쓴다).
- 분리 기동을 도입하면 **정지 경로를 같은 커밋에서 만든다.**
