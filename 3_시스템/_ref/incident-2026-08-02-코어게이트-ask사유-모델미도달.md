# 코어 게이트 준수사항 미도달 — `ask` 사유는 사용자 전용

## 증상

2026-08-02 `Edit(CLAUDE.md)` 실행 시 게이트는 정상 발동했고(`core-gate.log`에 기록) 사용자 화면에도 준수사항이 떴다. **그런데 Claude는 아무것도 받지 못했다.** 체크리스트를 따른 것은 Claude가 `_ref/`를 자발적으로 읽었기 때문이지 게이트 덕이 아니었다.

## 근본원인 — 설계 선택이 수신자를 갈랐다

공식 문서:

> **`'deny'`**: The reason appears as feedback to Claude about why the tool was blocked.
> **`'ask'`**: The reason is shown in the permission prompt **to the user (not to Claude directly as model context)**.

`core-gate.ps1`은 `permissionDecision = 'ask'`였다. **`ask`를 고른 순간 `permissionDecisionReason`은 모델에 도달할 수 없다.** 훅·로그·프롬프트 전부 정상이었고, 설계가 수신자를 사용자로 정한 것이다.

코어 게이트 착수 문구(*"매번 준수사항을 말해줘야함"*)의 **수신자가 모호했고**, 구현은 사용자로 해석됐다.

## 🔴 왜 검증이 통과했는가 — 검증 축이 운영 축과 반대였다

코어 게이트 설계 노트 255행: *"**R2 달성 확인**: 실환경 **서브세션**이 `permissionDecisionReason` 전문을 그대로 받았다."*

서브세션(`claude -p`)에는 **승인할 사람이 없다.** `ask`를 표시할 곳이 없으니 하네스가 차단으로 처리하고 사유를 모델 피드백으로 돌려준다 → 받았다.
대화형 세션에는 사람이 있다 → 프롬프트가 뜨고 **모델은 못 받는다.**

체크리스트 §2가 경고한 그것이다 — *"회귀 케이스가 '이번 변경이 건드리는 축'을 덮는가."* 07-30 게이트 성능 최적화 때와 **같은 실패 양식이 같은 파일에서 반복**됐다.

## 해결

`additionalContext`는 PreToolUse에서도 지원되며 *"Claude가 다음 모델 요청에서 보는 system reminder"*로 주입된다. `$reason`을 재사용해 두 경로가 어긋날 수 없게 했다.

```powershell
    permissionDecisionReason = $reason
+   additionalContext        = $reason
```

**검증**(격리 사본, `powershell` 5.1):

| 케이스 | 기대 | 결과 |
|---|---|---|
| Edit 코어 / Bash 코어+쓰기동사 / Write 훅신규 | 발동 | OK, `additionalContext` 1,375자 |
| Edit 비코어 / Read 코어 / Bash 코어+쓰기동사 없음 / Bash 비코어 | 미발동 | OK |

**실전 확인**: BOM 재저장 호출에서 7절 전문이 `system-reminder`로 실제 도달. **대화형 축 확인 완료.**

부수: `core-gate.ps1`만 UTF-8 **BOM이 없었다**(다른 훅 3개는 있음, 체크리스트 §6 위반). 재저장 +3바이트, 내용 불변. 지금까지 동작한 것은 `GetACP=65001` 덕이다.

## 비용

`additionalContext`는 발동 시 대화 계층에 ~1,000토큰이 들어가고 이후 요청에서 재독된다. **상시 0은 유지**되나 발동당 비용이 0이 아니다. 실운영 발동은 2026-08-02 기준 2회/일(그중 1회는 오발동).

## 잔여 위험 — 미해결, 별건

1. **정규식 파싱이 명령 문자열 안의 JSON에 속는다.** 로그에 실제로 하지 않은 `Edit CLAUDE.md`가 찍혔다. 검증용 stdin JSON을 담은 PowerShell 호출이 원인으로 보인다. 방향은 fail-safe(없는 발동을 만듦). **반대 방향(진짜 코어 접촉을 놓침)은 미검증.**
2. **쓰기 동사 목록 누락 후보 = fail-open.** `\bpython\d?\b`는 제작자 볼트의 표준 실행인 **`py -3`을 매치하지 않는다.** `WriteAllText` 등 .NET 직접 쓰기도 목록에 없다. 둘 다 코어 쓰기를 통과시킬 수 있다. **미검증 — 확인하려면 코어 대상 쓰기를 시도해야 해서 하지 않았다.**
3. 훅 주석은 성능(`ConvertFrom-Json` ~150ms) 때문에 정규식을 택했다고 적어뒀다. 1·2는 그 대가다.

## 잔여 위험 재검증 (2026-08-02, 격리 사본 · powershell 5.1)

### 1은 오진이었다 — 정규식 오탐은 없다

스푸핑 페이로드를 격리 사본에 직접 넣었다.

| 페이로드 | 로그 |
|---|---|
| PowerShell 명령 안에 가짜 `"tool_name":"Edit"`+`CLAUDE.md` | `PowerShell CLAUDE.md` |
| 같은 내용, `tool_input`을 `tool_name`보다 **앞에** 둔 순서 | `PowerShell CLAUDE.md` |
| 진짜 `Edit CLAUDE.md`(대조군) | `Edit CLAUDE.md` |
| 진짜 `Edit` 비코어 + `old_string` 안에 가짜 `file_path` | 미발동 |

도구명은 raw의 **첫** `"tool_name"`이고 그건 하네스가 쓴 값이라 명령 문자열이 덮을 수 없다. 필드 순서를 뒤집어도 §2가 셸 도구를 `command`로만 분기해 결과가 같다. `file_path`도 첫 매치가 진짜 값이라 본문 오염이 통하지 않는다.

**그럼 04:23:39 `Edit CLAUDE.md`는 무엇이었나 — 실제 편집이었다.** `38d7dfd`는 `CLAUDE.md`를 **2줄 교체**했다(§2 통독 규칙 + 도구 사용 규약). 04:06:31·04:23:39 두 발동이 그 두 줄에 대응한다. **로그가 맞았고 "하지 않았다"는 기억이 틀렸다.**

→ **로그를 의심하기 전에 산출물(`git show --numstat`)과 대조한다.** 관측 도구를 먼저 의심하면 없는 버그를 쫓는다.

### 2는 실재한다 — fail-open 확정

| 케이스 | 원본 | 기대 |
|---|---|---|
| `py -3 -c "open('CLAUDE.md','w')…"` | **미발동** | 발동 |
| `[IO.File]::WriteAllText('…/CLAUDE.md',…)` | **미발동** | 발동 |
| `python3 … CLAUDE.md`(대조군) | 발동 | 발동 |

**제약이 하나 있다** — `py`를 넓게 추가하면 안 된다. `py -3 3_시스템/search.py --eval`(weekly 4스텝)·`py -3 3_시스템/search.py "질의"`(search 스킬)가 §3에 걸린다. 발동시키면 **무인 실행이 승인 대기로 죽는다**(§7, [[incident-2026-07-27-weekly자동실행-권한대기-사망]]). 코어 스크립트를 *실행*하는 것과 코어를 *쓰는* 것을 갈라야 한다.

제안 패치 — 38행 쓰기 동사 목록 끝에만 추가(**승인 대기, 미적용**):

```
+|\bpy\s+(-\d(\.\d+)?\s+)?-c\b|WriteAll\w+|AppendAll\w+
```

12케이스 원본 대비 검증: 전부 기대 일치, **동작 변화는 1·2·11에 한정**(11 = `py -c`로 코어를 *읽는* 경우의 신규 오탐, fail-safe라 허용). weekly 4·8스텝, search 스킬, 읽기(`cat`·`Get-Content`·`ReadAllText`), 비코어 편집은 전부 미발동 유지.

**남는 구멍(정규식의 한계, 봉쇄 안 함)**: `py -3 fix.py CLAUDE.md`처럼 스크립트에 코어를 인자로 넘기는 형태 · `StreamWriter` 등 기타 .NET API · 명령 문자열에 코어 경로가 아예 안 나타나는 간접 쓰기. 완전 봉쇄는 `ConvertFrom-Json`(~150ms) 없이는 불가하고, 그 대가는 훅 주석 5~7행이 이미 인정한 것이다.

## 3축 동시 재확인 (2026-08-05) — 종결

`CLAUDE.md`에 임시 마커를 넣고 즉시 복원하는 2회 편집으로 세 축을 한 번에 관측했다. **전부 정상**이다.

| 축 | 관측 경로 | 결과 |
|---|---|---|
| 게이트 발동 | `core-gate.log` 69→71 | ✓ 2회 (`[auto]` 모드) |
| 프롬프트 표시 | 사용자 직접 확인 | ✓ 2회 |
| 모델 사유 도달 | `additionalContext` 수신 | ✓ 2회, 7절 전문 |

07-30의 *"발동 19건·프롬프트 0회 → auto가 게이트를 무력화한다"*는 판정이 이로써 **3번째로 반증**됐다(08-02 15행·53행에서 이미 두 축이 확인돼 있었다).

⚠ **이 재확인은 불필요했다.** 위 두 축의 답이 이 문서 15행과 53행에 이미 적혀 있었는데, Claude가 그것을 읽지 않고 "관측 불가·미해결"로 분류해 사용자 시간을 썼다. → **미해결로 분류하기 전에 해당 incident 본문을 끝까지 읽는다.**

## 재발방지

- **검증 환경이 운영 환경과 같은 축인지 먼저 묻는다.** 서브세션은 대화형의 대리가 아니다 — 승인 주체가 없다는 점에서 **정반대**다.
- **훅 출력 필드는 수신자를 명시적으로 확인한다.** `deny`=모델, `ask`=사용자. 둘 다 필요하면 `additionalContext`를 함께 낸다.
- `.ps1` 신규 작성 시 **BOM 확인을 절차에 넣는다**(§6). 미추적 파일은 `.gitattributes` 정규화를 받은 적이 없다.
