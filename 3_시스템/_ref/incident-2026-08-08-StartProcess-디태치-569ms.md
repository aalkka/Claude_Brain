# Start-Process 디태치는 공짜가 아니다 (+569ms)

## 증상

Stop 훅(`stop-check.ps1`)에 세션 스텁 갱신을 **비대기 디태치**로 얹었는데, 훅 왕복이 늘었다.

```
원본(HEAD)      942 1074 754 810 774ms   → 중앙 810ms
Start-Process   1350 1278 1384 1379 2361ms → 중앙 1379ms
```

**+569ms.** "디태치니까 비용 0"이라는 가정이 틀렸다.

## 원인

`Start-Process`는 결과를 기다리지 않아도 **프로세스 생성 자체가 Windows에서 무겁다.** `-WindowStyle Hidden` · `-ErrorAction SilentlyContinue`를 붙여도 마찬가지. 대기 시간이 아니라 **생성 비용**이다.

[[incident-2026-07-27-SessionStart-동기reindex-23초-블로킹]]과 같은 계열 — "비동기로 돌리면 된다"가 항상 성립하지 않는다.

## 해결

훅 안에서 프로세스를 띄우지 말고, **Claude Code가 직접 띄우게 한다.** 같은 이벤트에 훅 항목을 하나 더 등록하면 된다.

```json
"Stop": [
  { "hooks": [ { "type": "command", "command": "py -3 \"$CLAUDE_PROJECT_DIR/3_시스템/session-stub.py\"" } ] },
  { "hooks": [ { "type": "command", "command": "powershell ... stop-check.ps1" } ] }
]
```

**569ms → 207ms.** 그중 160ms가 python 인터프리터 기동이고 실제 작업은 12~47ms다.

부수 이득: `stop-check.ps1`을 안 건드리므로 [[코어수정-준수사항-체크리스트]] §4("stop-check는 손대지 않는다")를 지킨다. **성능 문제와 규약 충돌이 같은 해법으로 풀렸다.**

## 후속 — 이 "해결"은 하루 동안 적용되지 않았다 (2026-08-09 확인)

위 해결은 **문서에만 존재했다.** 08-09에 배포판 작업 중 확인해보니 `stop-check.ps1`에 `Start-Process` 블록이 그대로 살아 있었다.

- 현재 워킹트리 블롭 = `410428e` = **`af08470`의 결과와 바이트 동일**. 되돌리기가 파일에 반영된 적이 없다.
- 한 세션의 스텁 타임라인: `14:39 수정 stop-check.ps1` → **`14:40:59` Stop 훅 자동 커밋 `af08470`**(author `Claude`, 메시지 `session: 2026-08-08`) → `14:40~14:42` 회귀 테스트와 함께 `Revert stop-check.ps1 to original` 실행.
- 되돌리기가 자동 커밋 **뒤에** 돌았고, 그 뒤 `stop-check.ps1`을 건드린 커밋이 하나도 없다 → 워킹트리가 계속 수정본이었다.

결과: `settings.json` 경로와 훅 내부 경로가 **둘 다 활성**인 채로 돌았다. `session-stub.py`의 60초 락이 실작업 중복은 막았으나 프로세스 생성 비용은 그대로 물었다.

**08-09 복원**: `git checkout af08470^ -- 3_시스템/hooks/stop-check.ps1`로 원본 블롭 `7df83dc` 복원(바이트 일치·BOM 보존·CRLF 0). PS 5.1 파싱 OK, stdout 0바이트, fail-open 4케이스 exit 0.

### 실측 정정 — +569ms는 조건부였다

복원 전후를 같은 조건에서 재보니 델타가 훨씬 작았다.

| 구간 | 중앙값 | 범위 | 표본 |
|---|---|---|---|
| 블록 있음 | 936ms | 903~1079 | 7 |
| 블록 제거 | **801ms** | 792~826 | 11 |
| 델타 | **−135ms** | | |

원 측정의 569ms가 재현되지 않았다. 추정 원인 = **당시엔 `.state-*.json`이 없어 자식이 전량 파싱(197ms)을 돌았고**, 지금은 증분(12ms)이라 자식이 훨씬 빨리 끝난다. `Start-Process`가 비대기여도 자식이 부모와 파이프를 공유하면 부모 왕복에 일부가 잡힌다. 즉 **569ms는 "첫 실행·전량 파싱" 조건의 값이고 정상 운영(증분) 조건에서는 135ms다.** 원 측정에 이 조건이 기록되지 않았다.

방향(훅 안에서 spawn하지 말 것)은 그대로 유효하다. 크기만 정정한다.

### 진짜 교훈 — 성능이 아니라 절차

1. **Stop 훅의 자동 커밋이 코어 실험의 중간 상태를 박제한다.** 되돌리기 전에 훅이 먼저 커밋하고, 메시지가 `session: 날짜`라 나중에 봐도 무엇을 했는지 모른다. → open-loops의 *"코어 수정은 그 턴 안에 수동 커밋"*이 정확히 이 양식을 겨눈 규칙인데 지켜지지 않았다.
2. **되돌리기는 실행했다고 끝이 아니다.** 되돌린 뒤 `git hash-object`로 목표 블롭과 대조해야 한다. 이번엔 "revert를 실행했다"는 사실만으로 문서에 "불변"이라 적었다.
3. **복원은 편집보다 싸고 강하다.** 목표 상태가 git에 있으면 새로 편집해 회귀 6케이스를 돌릴 게 아니라 블롭을 꺼내 해시를 대조한다 — BOM·EOL·한글 오염 가능성이 원리적으로 0이 된다.
4. weekly-review 7스텝(`session:` 익명 코어 커밋 계수)은 `af08470`을 잡도록 설계돼 있었으나, 08-08 이후 weekly가 돌지 않아 아무도 보지 않았다. **계측기는 돌아야 계측기다.**

## 같은 양식이 복원 작업 중 재현됐다 (2026-08-09, 실측 2건째)

위 복원을 하면서 정확히 같은 일이 또 일어났다.

- `11:00:46` Stop 훅 자동커밋 `5a5bcfc`(`session: 2026-08-09`)가 **12줄 삭제를 담아갔다.**
- 그 뒤 낸 수동 커밋 `b9567fd`에는 문서 2건만 남았다 — 근거와 코어 변경이 서로 다른 커밋으로 갈렸다.

결과는 옳다(블롭 `7df83dc`, HEAD 일치). 08-08과 달리 이번엔 **기록만** 갈렸다. 그러나 양식은 동일하다.

### 규칙이 실행 불가능하다

open-loops의 *"코어 수정은 그 턴 안에 수동 커밋"*은 현 구조에서 지킬 수 없다.

- Stop 훅은 **턴이 끝날 때** 돈다. 코어를 고친 턴이 끝나는 순간 훅이 먼저 커밋한다.
- 다음 턴에 수동 커밋해봐야 이미 잡혀간 뒤다.
- 한 도구 호출 안에서 `수정 && commit`을 묶으면 지킬 수 있으나, 그러면 **커밋 전 검증을 할 수 없다.**
- 즉 **"검증 후 커밋"과 "그 턴 안에 커밋"이 양립하지 않는다.** 08-08·08-09 둘 다 이 벽에 걸렸다.

### 우회로 — 오늘 배포판 작업에서 실제로 통한 방법

같은 날 배포판 이식은 이 문제를 겪지 않았다. **`git worktree`로 볼트 밖에서 작업**했기 때문이다. 볼트 본체 파일이 바뀌지 않으니 Stop 훅이 잡을 것도 없고, 검증을 끝낸 뒤 원하는 시점에 커밋할 수 있었다.

일반화하면: **코어 파일을 고칠 땐 볼트 본체를 마지막 순간까지 건드리지 않는다.** 수정본을 볼트 밖(worktree·스크래치패드)에 두고 검증을 끝낸 다음, `복사 && add && commit`을 한 호출로 묶는다. 이러면 검증과 원자적 커밋이 동시에 성립하고 코어(stop-check) 수정도 불요다.

**결론 (2026-08-17)**: 이 우회로는 **권장 수단으로 채택**한다 — 필수 절차는 아니다. 같은 날 방지층 전반을 조사한 결과 `stop-check`에서 코어 경로를 빼는 안(및 별도 ref 스냅샷 안)은 **기각**됐다: 절차 존재 이후 익명 코어 커밋 5건이 **전부 근거 문서를 갖고 있어**(소실 0) 체크리스트 §0("이미 있는 것으로 되는가")를 통과하지 못한다. 대신 `weekly-review` 7스텝이 익명 코어 커밋마다 근거 문서를 대조한다. 전문 → [[incident-2026-08-02-git-index-lock-62시간-자동커밋사망]] §2026-08-17.

이 우회로의 한계도 같이 적어둔다 — 규약층이라 모델이 지켜야 한다. 게이트 준수사항이 매 코어 접촉마다 뜨는데도 08-16 `683fafa`가 발생했다. 즉 "절차를 문서에 적었으니 지켜진다"는 가정은 제작자 볼트에서 이미 반증됐다.

## 교훈

1. **디태치를 비용 0으로 가정하지 말고 잰다.** 훅은 발동마다 도는 자리라 수백 ms가 누적된다.
2. **런처가 이미 프로세스를 띄울 수 있으면 그쪽에 맡긴다.** 훅 시스템이 여러 command를 지원하면 직접 spawn하지 않는다.
3. 훅에서 파이썬을 쓸 때 지배 비용은 작업이 아니라 **인터프리터 기동**(160ms)이다. 증분화로 작업 시간을 12ms까지 줄여도 총 시간은 기동이 정한다.
