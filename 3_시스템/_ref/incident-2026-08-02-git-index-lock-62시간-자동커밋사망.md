# git index.lock 62시간 잔존 — 자동커밋 조용한 사망

## 증상

2026-08-02 커밋 시도가 실패했다.

```
fatal: Unable to create 'C:/Claude_Brain/.git/index.lock': File exists.
```

락 실물:

```
크기      0 바이트
생성      2026-07-30 14:08:32
수정      2026-07-30 14:08:33
경과      3,744분 ≈ 62시간
git 프로세스  없음
```

마지막 커밋은 `07c1384 session: 2026-07-30`. **07-30 14:08부터 모든 커밋이 막혀 있었다.**

## 그 사이 쌓인 미커밋 산출물

코어 게이트 1·2층 구축 · 준수사항 체크리스트 · 결정 기록 · 골든셋(`golden.jsonl`·`golden-paraphrase.jsonl`) · `results-weekly.md` · 세션노트 2건 · `tokens.py` · 결정 기록 · incident 3건 — **37파일 / +2,446줄**이 한 커밋(`38d7dfd`)으로 몰렸다.

## 근본원인

07-30 14:08의 git 작업이 중단되며 0바이트 락을 남겼다. 이후 모든 `git add`/`commit`이 이 락에 막혔다.

**진짜 문제는 락이 아니라 침묵이다.** SessionEnd 자동커밋이 매 세션 실패했는데 **어떤 신호도 없었다.** 62시간 동안 아무도 몰랐다.

## 조치 (임시)

락을 **삭제하지 않고 격리**했다 — `.git/index.lock.stale-20260802`.
※ `Remove-Item`은 프로젝트 경로 보호 규칙에 막힌다. `Move-Item`으로 우회했고, 이쪽이 되돌릴 수 있어 더 낫다.

이후 `git add -A` → `38d7dfd` 커밋 성공, 잔여 미커밋 0.

## 🔴 미해결 — 탐지 경로가 없다

**이 유형은 제작자 볼트에서 세 번째다.**

| 사례 | 실패 | 왜 몰랐나 |
|---|---|---|
| [[incident-2026-07-27-weekly자동실행-권한대기-사망]] | 무인 weekly가 승인 대기로 abort | `lastRunAt`이 발화 시각만 기록 → UI엔 성공 |
| [[incident-2026-07-19-SessionEnd-커밋정지]] | SessionEnd 커밋 정지 | — |
| 이 건 | 62시간 커밋 차단 | 자동커밋 실패에 신호 없음 |

**공통 = 실패가 조용하다.** 성공 신호를 산출물로 확인하지 않으면 못 잡는다.

**후보 대책**(미채택, 별건):
- weekly가 **마지막 커밋 경과시간**을 보고 — 24시간 초과 시 경고. 계측만이라 비용 0.
- SessionEnd 훅이 커밋 실패를 stderr로 남기고 다음 SessionStart가 보고.
- `index.lock` 존재 + git 프로세스 부재를 세션 시작 시 1회 확인.

**첫 번째가 가장 싸다** — weekly-review 6스텝(헬스)에 한 줄이면 된다.

## ✅ 조치 (2026-08-02) — 탐지 경로 신설

첫 번째 후보를 채택했다. `weekly-review` **6스텝(헬스)**에 한 줄:

> **마지막 커밋 경과시간**(`git log -1 --format=%cr`) — **24시간 초과면 경고**.

- **비용 0.** 읽기 전용 1회, 승인 프롬프트가 뜨지 않아 무인 실행에서 안전하다(체크리스트 §7).
- weekly SKILL.md는 코어가 아니므로 게이트·ADR 대상이 아니다.
- **한계**: 주 1회 해상도다. 24~168시간 사이의 사망은 최대 일주일 늦게 잡힌다. 더 촘촘한 탐지(SessionStart의 `index.lock` 존재 확인)는 코어(`settings.json`) 수정이라 별건으로 남긴다 — **2번째 실측이 나오면 그때.**

## ✅ 재조사 종결 (2026-08-03) — 훅 수정 불요

"자동커밋이 코어 변경을 익명으로 삼킨다"를 다시 조사했다. **결론: 훅을 고칠 일이 아니다. 이 항목으로 재조사하지 마라.**

**정체** — `3_시스템/hooks/stop-check.ps1:84`. 검증 통과 시 **매 턴 끝**에 `git add -A` → `commit -m "session: <날짜>"`. 버그가 아니라 **의도된 설계**다(주석 78~80행): 실제 종료 = PC 셧다운이라 SessionEnd가 OS에 kill되므로 커밋을 살아있는 턴 종료로 옮겼다. 목적은 이력 서술이 아니라 **durability** — [[incident-2026-07-19-SessionEnd-커밋정지]]의 시정 결과다.

**왜 추가 조치를 안 하는가** — 체크리스트 §0("이미 있는 것으로 되는가")을 통과하지 못한다. 탐지가 완비돼 있다:

| 경로 | 무엇을 잡나 |
|---|---|
| weekly 6스텝 | 마지막 커밋 경과시간 24h 초과 경고 |
| weekly 7스텝 | 코어 변경 커밋 수 + **그중 `session:` 익명 비율** + 해시 나열, 게이트 발동수와 교차검증 |
| `_index/core-gate.log` | 게이트 발동 실기록(08-03 18:44 CLAUDE.md 편집 정상 기록 = 게이트 생존 확인) |

커밋 제목에 `[core]` 표시를 붙이는 안을 검토했으나 **새 정보를 만들지 않는다** — weekly 7스텝의 경로 필터가 이미 정확하고 제목 표시는 육안 스캔을 앞당길 뿐이다. 대가는 코어 훅 수정 + 격리 검증(§2) + ADR.

**남는 것은 습관이지 코드가 아니다.** 코어를 고쳤으면 **그 턴 안에** 명시적으로 커밋한다. Stop 훅은 미커밋분을 다음 턴에 삼킨다 — 08-03에 CLAUDE.md 한 줄이 `6000fdf`로 삼켜졌고 `d14cbec`로 amend 복원했다(미푸시라 안전).

**카운트 정정** — 같은 날 `6c14035`가 `deep-loop/SKILL.md`를 삼켰으나 **스킬 파일은 코어가 아니다**(게이트·절차 대상 아님). 코어 익명화는 `2de52b3`·`a974f9c`·`6000fdf` 3회.

## ✅ 후속 종결 (2026-08-17) — 방지층도 짓지 않는다

08-03은 **탐지** 범위에서 "훅 수정 불요"를 판정했다. 08-08·08-09·08-16에 같은 양식이 재발하자 **방지** 범위(자동커밋이 코어를 삼키기 전에 막는 층)를 별도로 조사했다 — 08-03이 검토하지 않은 영역이므로 재조사 금지에 걸리지 않는다. 6루프 조사 결과 **방지층도 짓지 않는다.**

**08-03의 세 부분 중 무엇이 살고 무엇이 죽었나**

| 08-03이 남긴 것 | 판정 |
|---|---|
| (a) 매 턴 커밋은 버그가 아니라 durability 설계 | **유효** — 반증 0 |
| (b) "[core] 제목 표시" 기각(새 정보 0) | **유효** — 방지층 후보들도 같은 자리에 걸린다 |
| (c) 처방 "코어를 고쳤으면 그 턴 안에 수동 커밋" | **폐기** — 08-09에 원리적 실행 불가 판명 |

(c)가 불가능한 이유: Stop 훅은 턴이 끝날 때 돈다. 한 도구 호출에 `수정 && commit`을 묶으면 지킬 수 있으나 그러면 커밋 전 검증을 못 한다. **"검증 후 커밋"과 "그 턴 안에 커밋"이 양립하지 않는다** → [[incident-2026-08-08-StartProcess-디태치-569ms]] §규칙이 실행 불가능하다.

**방지층을 기각한 근거 — 볼트 전수 측정 3건**

| 측정 | 값 | 함의 |
|---|---|---|
| 07-19 durability 도입이 지키려던 것 | **세션노트 6일치**. 코어 파일 유실 **0건** | "코어를 자동커밋에서 빼면 durability가 깨진다"는 반론이 성립 안 함 |
| 메인 이력의 익명 체크포인트 비율 | **73.6%** (214/291) | git 이력이 이미 checkpoint 스트림. 코어만 record를 요구하는 것이 비일관 |
| 절차 존재(07-31) 이후 익명 코어 커밋의 근거 문서 | **5건 중 5건 존재**(`683fafa`·`5a5bcfc`·`af08470`·`2de52b3`·`38d7dfd`) | **정보 소실 0.** 실손해는 "`git log`→문서 한 단계 우회"뿐 |

세 번째가 결정적이다. 체크리스트 §0("이미 있는 것으로 되는가")에서 걸린다 — 근거가 100% 남아 있으므로 어떤 방지층도 **새 정보를 만들지 않는다**. (b)를 기각한 논리와 같은 자리다.

추가로 `stop-check.ps1`은 매 턴 도는 커밋 경로이고 제작자 볼트는 그 경로에서 두 번 다쳤다(07-19 한 주 정지, 08-02 62시간). 얻는 것이 "접근 편의"인데 잃을 수 있는 것이 "커밋 정지"면 비대칭이다.

**검토하고 기각한 안**
- **B: `stop-check`에서 코어 5경로 pathspec 제외** — 문법은 제작자 볼트에 이미 실증돼 있다(`stop-check.ps1:84`의 `':!1_수집'`). 기각 사유 = §0(새 정보 0) + 매 턴 커밋 경로 수정 위험 + 체크리스트 §4("stop-check는 손대지 않는다").
- **D: 코어를 메인 커밋에서 빼되 별도 ref(`GIT_INDEX_FILE`→`write-tree`→`commit-tree`→`update-ref`)에 스냅샷** — durability 손실 0으로 B의 약점을 없애지만 표면이 더 크다. 같은 §0에서 걸린다.
- **E: `git notes`로 사후 근거 부착** — 기본 push/fetch 안 되어 설정 2줄 + 배포판 설치 절차 증가. 아래 채택안이 스크립트 없이 같은 일을 한다.

**채택 = 현행 유지 + `weekly-review` 7스텝 한 줄.** 7스텝은 이미 익명 코어 커밋 해시를 나열한다. 거기에 **같은 날짜 근거 문서를 함께 적는다**를 더해 유일한 실손해(한 단계 우회)를 없앤다. 코어 수정 0 · ADR 불요(weekly SKILL은 코어 아님) · durability 무손상 · 실행 지점이 정례 절차라 습관 의존 아님.

**worktree 우회로는 강등**(폐기 아님) — 필수 절차가 아니라 **코어를 실제로 고칠 때의 권장 수단**. 검증과 원자적 커밋을 동시에 얻는 유일한 방법이라는 점은 유효하나, 규약층이라 모델 의존이고 게이트 준수사항이 이미 같은 층에서 실패한 전례가 있다(08-16 `683fafa`는 게이트 텍스트가 매 접촉마다 떴는데도 발생).

**카운트 정정** — "코어 익명 커밋 3회"는 08-08 이후만 센 것이었다. 전수는 **43건 중 22건(51%)**, 절차 존재 이후로 좁히면 **5건**. 07-30 이전 17건은 게이트·체크리스트 신설 전이라 위반이 아니다.

**미확인 (이 조사에서 확정 못 함)**
1. 훅 계약에 `PostToolBatch`(block 가능·모델 호출 전)·`PermissionRequest`(승인 결정 시점)·`WorktreeCreate`가 존재하나 **제작자 볼트 환경에서 발화하는지 미검증**. 특히 `PermissionRequest`는 아래 3번의 관측 불가 제약을 푸는 후보다. 확정법 = 각각 `hooks.log` 한 줄 쓰는 훅을 걸고 한 세션 관측.
2. 절차 부재기(07-30 이전) 익명 코어 커밋 17건에 근거가 남았는지는 세지 않았다.
3. 코어 접촉 시 승인 프롬프트가 실제로 뜨는지는 여전히 Claude가 관측할 수 없다(체크리스트 §관측). 07-30에 이걸 착각해 오판한 전례가 있으므로 **로그의 `[auto]` 표기만 보고 "게이트 무력화"라 판단하지 말 것** — 2026-08-17 조사 중 같은 오판이 한 번 재현됐다가 체크리스트를 읽고 철회했다.

## 재발방지 (원칙)

- **자동화의 성공은 실행 기록이 아니라 산출물로 판정한다.** `lastRunAt`·"오류 없음"은 증거가 아니다.
- **조용히 실패하는 경로마다 카운터를 둔다.** 트리거만 있고 카운터가 없으면 조건이 영원히 미충족이다(체크리스트 §0의 같은 교훈).
